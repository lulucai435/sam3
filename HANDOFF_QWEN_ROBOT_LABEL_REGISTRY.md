# Handoff: Build an OXE Robot-Related Label Registry with Qwen

## 1. Goal

Add a standalone offline script to `/public/home/lulucai/code/sam3` that:

1. scans all existing OXE SAM3 `metadata.json` files;
2. collects every unique object label generated by Qwen/Gemini;
3. calls Qwen to classify every unique label;
4. produces a reviewed machine-readable registry of all robot-related names.

The registry will be consumed by the Stage 1 loader in
`/public/home/lulucai/code/hypolicy-target`. Robot-related masks will be unioned
with each non-robot object's mask, and robot-related labels will no longer be
emitted as standalone segmentation samples.

This task only builds the audit/classification script and output registry. Do
not modify existing SAM3 masks or overwrite episode metadata.

## 2. Existing Project Context



## 4. Vocabulary Scan

For every raw label, record:

- exact raw string;
- normalized string;
- occurrence count;
- dataset names in which it occurs;
- up to a small configurable number of example `metadata.json` paths;
- optionally associated language instructions for audit context.

Normalization must be deterministic:

1. Unicode NFKC normalization;
2. lowercase;
3. trim surrounding whitespace;
4. convert underscores, hyphens and punctuation to spaces;
5. collapse repeated whitespace.

Do not merge away the raw spellings. Multiple raw variants may map to the same
normalized label and should remain visible in the vocabulary report.

Write the vocabulary report before calling Qwen so scan results survive API
failure:

```text
reports/oxe_robot_labels/object_label_vocabulary.json
```

Include scan statistics:

- metadata files scanned;
- malformed/unreadable files;
- total label occurrences;
- unique raw labels;
- unique normalized labels;
- datasets covered.

## 5. Qwen Classification

Classify every unique normalized label, not only keyword-filtered candidates.
Unexpected robot names are the reason for using Qwen.

Batch labels to reduce API cost, but require one output entry for every input
label. Use stable numeric IDs in the request so duplicate/similar strings cannot
be confused.

Required classification schema:

```json
{
  "id": 17,
  "label": "black robotic arm",
  "is_robot_related": true,
  "canonical_category": "robotic_arm",
  "confidence": 0.99,
  "reason": "A robotic manipulator arm."
}
```

Allowed `canonical_category` values:

```text
robotic_arm
gripper
end_effector
non_robot
uncertain
```

Semantics:

- `robotic_arm`: the robot arm/manipulator and clearly identified parts of that
  arm, including color/material variants, robot base, robot joint and robot link;
- `gripper`: gripper, claw or gripping mechanism;
- `end_effector`: end effector, robot hand/wrist/tool flange when it denotes
  the robot's terminal mechanism;
- `non_robot`: environment object, person, human body part, support surface,
  tool or other non-robot entity;
- `uncertain`: insufficient semantic certainty from the name/context.

For this pipeline, `is_robot_related` must be true only for:

```text
robotic_arm
gripper
end_effector
```

Set it to false for `non_robot` and `uncertain`. For `uncertain`, keep it false
until manual review assigns one of the three included categories.

Important examples:

```text
robotic arm       -> robotic_arm
black robotic arm -> robotic_arm
robot arm         -> robotic_arm
mechanical arm    -> robotic_arm or uncertain depending on context
manipulator       -> robotic_arm
gripper           -> gripper
claw              -> gripper or uncertain depending on context
end effector      -> end_effector
robot hand        -> end_effector
robot wrist       -> end_effector
robot base        -> robotic_arm
robot joint       -> robotic_arm
robot link        -> robotic_arm
person            -> non_robot
human hand        -> non_robot
table             -> non_robot
```

The prompt must state that classification concerns robot-manipulation datasets,
but Qwen must not classify a generic label as robot-related solely because it
contains `arm`, `hand`, `claw` or `wrist`.

Use:

- low temperature, preferably `0` or `0.1`;
- strict JSON-only output;
- response validation;
- retry with backoff for network/API/parse failures;
- configurable batch size and request timeout.

If a response omits, duplicates or changes an input ID/label, reject the batch
and retry. Never silently accept a partial classification.

## 6. Resume, Cache and Reproducibility

API classification must be resumable.

Append validated batch results to a JSONL checkpoint such as:

```text
reports/oxe_robot_labels/qwen_classification_checkpoint.jsonl
```

On restart:

- load already classified normalized labels;
- skip them;
- classify only missing labels;
- preserve the original result unless `--force-reclassify` is passed.

Record:

- model name;
- prompt/schema version;
- timestamp;
- normalized input label;
- raw API response or a hash/reference sufficient for debugging.

Do not put API keys in reports, logs or source files.

## 7. Required Outputs

### Full classification table

```text
reports/oxe_robot_labels/all_label_classifications.json
```

Contains every normalized label, raw variants, counts, examples and final Qwen
classification.

### Robot-related registry

```text
reports/oxe_robot_labels/robot_label_registry.yaml
```

Recommended structure:

```yaml
version: 1
source_root: /public/home/lulucai/data/oxe_seg
qwen_model: qwen3-vl-flash
prompt_version: robot-label-v1

categories:
  robotic_arm:
    - black robotic arm
    - robot arm
    - robotic arm
  gripper:
    - gripper
  end_effector:
    - end effector
    - robot hand
    - robot wrist

labels:
  black robotic arm:
    category: robotic_arm
    is_robot_related: true
    confidence: 0.99
    count: 1234
    raw_variants:
      - Black robotic arm
      - black_robotic_arm
```

Lists must be deduplicated and sorted for stable diffs.

### Manual-review table

```text
reports/oxe_robot_labels/uncertain_labels.csv
```

Include:

- normalized label;
- raw variants;
- count;
- Qwen reason/confidence;
- datasets;
- example metadata paths;
- blank columns for human decision and canonical category.

Also include low-confidence robot/non-robot decisions under a configurable
threshold, not just explicit `uncertain` outputs.

### Summary

```text
reports/oxe_robot_labels/summary.md
```

Report:

- scan/classification totals;
- robot-related label count by category;
- total occurrences covered by robot-related labels;
- uncertain/low-confidence labels;
- top robot-related labels by occurrence;
- Qwen/API failures still unresolved.

## 8. Manual Overrides

Support an optional override file:

```text
reports/oxe_robot_labels/manual_overrides.yaml
```

Example:

```yaml
mechanical arm: robotic_arm
claw: gripper
human hand: non_robot
```

Final output precedence:

```text
manual override > validated Qwen result
```

Validate override categories against the allowed category set. Record in the
final table whether a decision came from `qwen` or `manual_override`.

The generated registry should be usable without manual overrides, but uncertain
entries must not be included as robot-related until reviewed.

## 11. Guardrails

- Do not rewrite any existing `metadata.json`.
- Do not rerun SAM3.
- Do not classify only labels matching an English keyword filter.
- Do not call Qwen once per metadata file; classify deduplicated labels in
  batches.
- Do not call Qwen from the Stage 1 training loader.
- Do not automatically include `uncertain` labels as robot-related.
- Do not store `DASHSCOPE_API_KEY` in code or output.
- Do not treat generic `arm`, `hand`, `claw` or `wrist` as robot-related without
  Qwen/contextual classification or manual review.
